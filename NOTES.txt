Static Vercel site: no Next.js middleware. Dashboard HTML is in private/index.html and served only by api/site.js after signed-cookie verification. Configure secrets in Vercel environment variables.
Staff Performance page: private/staff.html, served by api/site.js at /staff after verifying the staff_auth cookie. Shared auth helpers: api/_projects.js. Env vars: STAFF_USERNAME, STAFF_PASSWORD.
Sales person dashboard: private/person.html, served by api/site.js at /staff/person?store=...&name=... (same staff_auth cookie). Opened by clicking a name on the Staff Performance table. It reads the query already loaded in the browser (storeStaffSummary.v1); nothing is stored on the server. Rows now keep date and item (columns Item Code / Item Name when present) so load the query file once again to unlock daily trend, weekday and top-product charts.
Staff Performance roles (api/_projects.js): super admin = STAFF_USERNAME / STAFF_PASSWORD (sees everything). Area managers: MANAGER_CAIRO_USERNAME / MANAGER_CAIRO_PASSWORD (Cairo zone: Almaza, City Stars, CFC, Point 90) and MANAGER_OCT_USERNAME / MANAGER_OCT_PASSWORD (October & Alexandria zone: Mall of Egypt, Mall of Arabia, Alexandria). All use the Staff Performance button on the login page. Usernames must all be different. A manager account only works when both its username and password are set. Zones match store names loosely (ZONES in api/_projects.js); a store matching no zone is visible to the super admin only, and the super admin page lists such stores. Sales data is still held only in each browser, so zone filtering controls what the page shows, it is not server-side protection.
Server storage + staff accounts: sales data is now kept in a PRIVATE Vercel Blob store (pandora-data, BLOB_READ_WRITE_TOKEN added to the project automatically). The super admin loads the Query Report once on /staff; the page publishes it (api/data.js). The server then sends each person only what they may see: super admin everything, managers their zone's stores, sales people only their own rows plus store/company totals (api/_stats.js). If the store is not configured the pages fall back to the old browser-only mode.
Sales people sign up at /signup.html (always open, no SMS code): name, store, phone, username, password. The account is pending. The super admin opens 'Staff approvals' (button on /staff, page /staff/accounts), picks the matching sales person from the published file and approves; only then can the person sign in and see their own page. Passwords are stored as scrypt hashes; 8 wrong passwords lock an account for 15 minutes; sign-up is limited to 6 tries per visitor per hour. The admin must publish the monthly query on /staff once so sales people can be linked.
/api/health shows which parts are ready (storage, which manager accounts exist). It returns no secrets or people.

One login for everything: /login.html has only username + password (no project buttons). api/login.js checks every kind of account (super admin, area managers and approved sales people; the old separate dashboards login PANDORA_USERNAME/PASSWORD was removed and is ignored). The home screen (/, private/home.html) lists what that person can open, from api/_apps.js. To add a new option later, add one entry to APPS in api/_apps.js (id, title, description, href, and who may see it) and create the page. A person with only one option is sent straight to it. Super admin: Dashboards + Staff Performance. Area managers (Joseph, Hassan): Staff Performance + Pandora Dashboards, both limited to the stores of their zone (the server filters the Dashboards sales lines by store name with the same ZONES rules, api/uploads.js; they can read only, never upload or manage). Area manager passwords can be changed by the super admin on Staff approvals; a changed password is stored hashed (users/envpw/) and replaces the Vercel one. Pandora Dashboards is at /dashboards. Sales people: My sales. Log out clears every session.

Forgot password: /forgot.html (link on the login page). The sales person types the phone number of their account; nothing is sent to the phone. The request (resets/<username>.json) shows on the super admin's Staff approvals page under 'Forgot password requests' with the phone number to call; the admin sets a new password (Change password) which clears the request, or dismisses it. Limited to 6 tries per visitor per hour.

Special accounts (VM): the super admin creates them on the Staff approvals page under 'Special accounts' (name, username, password, access). The VM account (Raef Wengat) signs in with the same login and is sent straight to /vm, the VM Report. He cannot open Staff Performance, Dashboards, sales data or any admin tool (api/data.js and api/accounts.js refuse him). The super admin feeds the report on /vm by choosing an Excel file (all sheets are stored in the private store at vm/current.json, api/vm.js); the VM account only views it. The page currently shows the sheets as tables; the dashboard visuals get built from the real Excel sheets.

VM REPORT LIBRARY
- /vm shows a list of reports; the VM (Raef) picks one. The super admin adds reports by dropping an Excel file on that page (Remove button per report).
- Amounts are ALWAYS stripped on the server (api/vm.js): only columns like store/category/item/qty are kept; anything named amount/value/price/revenue/TRX/etc. is dropped, and "Total" rows are ignored. Nothing with amounts is ever stored or sent to the VM.
- Report kinds: "qty-by-category" (store + category + qty) gets the full dashboard (bars, heat map, store cards, filter; Packaging/Operations hidden by default with a toggle); any other file shows as a simple table. New kinds can be added in private/vm.html.

ALL UPLOADS (super admin home screen -> "All Uploads", /uploads)
- One page listing every document under the part of the site it feeds: Pandora Dashboards, Staff Performance, VM Report. Each section has Add a file / drop zone and a Remove button per document (two-step: "Sure? Remove").
- Pandora Dashboards sales files are now saved on the server (dash/index.json, dash/f/<id>.json, api/uploads.js) and load automatically every time the dashboard opens. They are only removed with Remove on the All Uploads page. Several files are added together; a line that appears in two files is counted once; adding a file with the same name replaces that file.
- The Upload button on the Dashboards page saves into the same place (it no longer keeps data in the browser only).
- Staff Performance data (one month, data/current.json) and VM reports (vm/) are listed here too and can be removed here; their own upload buttons still work.
- Shared file readers: private/parsers.js (window.PandoraParse), served to the super admin only.

ERP SYNC (api/erp.js)
- Pulls "Sales Report by Item & SKU" into Pandora Dashboards (saved as dash/f/erp-YYYY-MM.json, one file per month, replaced on each sync) and "Sales Person-wise Transaction Summary By Store" into Staff Performance (data/current.json).
- Super admin: "Sync from ERP" card on All Uploads (pick a month, Sync now). Vercel cron (vercel.json) syncs the current month every day at 04:00 UTC.
- Env vars: ERP_URL, ERP_API_KEY, ERP_API_SECRET (read-only ERPNext user), CRON_SECRET (any long random text; Vercel sends it to the cron call).

VM ZONES (/vm/zones, private/vmzones.html, api/_vmzones.js reached at /api/vmzones via a rewrite to api/vm.js: the Hobby plan allows 12 functions, so new APIs must be _helpers routed through an existing function)
- Super admin and the VM account: pick a store, see its zones on the floor plan, place a collection in a zone from a start date (the previous one in that zone ends that day), compare two placements, download an Excel report (Placements with start/end dates and results, Daily, Notes).
- Zones are numbered right to left as you face the store from the entrance (entrance = bottom of the plan); numbers are recalculated whenever the layout is saved. "Edit zones" = drag, resize, add, remove, name the location.
- Floor plans / photos per store (PDF, JPG, PNG, WEBP, up to 25 MB, uploaded in pieces under Vercel's 4.5 MB limit). Ticking "Use as floor plan" on a PDF asks for the page and saves that page as an image behind the zones.
- Results = the store's sales of that collection while it was in the zone (ERP does not record sales per zone). The collection comes from the ERP item group ("Pandora Moments - Charm" -> Moments), saved as the 11th column of ERP sales lines (api/erp.js); lines from older Excel uploads borrow it by SKU. Run Sync from ERP once so collections appear.
- Money: the super admin sees EGP; the VM account sees pieces, UPT, ATV, shares, a sales index (% of the store's average day) and % changes, never sales totals.
- Storage: vmz/<store>.json (zones, placements, files), vmz/f/<store>-<id>-<n>.json (file pieces). Shared sales reader: api/_sales.js.
- What the VM account sees: the super admin ticks/unticks parts on the VM Zones page (zone panel, impact comparison, daily chart + daily sheet, Excel report, floor plans/photos). Saved in vmz/settings.json and enforced on the server (hidden data is not sent).
- Item lists: instead of a whole collection, a placement can be an Excel list of items (columns SKU and/or DV; no headings = first column read as SKUs). A DV counts every size of that design (395078C01 matches 395078C01-45, -50...). The zone panel shows the items that sold; the Excel report adds Items (every item sold per placement) and Lists (the codes of each uploaded list).

STAFF PERFORMANCE DATES: every Staff Performance page (/staff and the sales person page /staff/person, /staff/me) has From / To date boxes plus "Last 7 days" and "Whole period", for every role. The page asks /api/data?from=YYYY-MM-DD&to=YYYY-MM-DD and the server keeps only rows whose day (row column 5) is inside the range (byDate in api/data.js), so sales people never receive more than their own rows and the store/company comparison numbers follow the same dates. The response always carries dayMin/dayMax (the whole file) so the boxes know their limits. Dates stay in the page address (?from=&to=) and are carried from the list to a person's page and back. Hidden when the data is browser-only (no server storage) or the file has no dates.

SALES BY COLLECTION (Pandora Dashboards, private/index.html, section above the Category explorer): sales grouped by Pandora family (Moments, Timeless, Essence ...). The collection is the 11th column of ERP sales lines (api/erp.js); older Excel lines borrow it from any line with the same SKU; anything left is shown as "Not classified". It uses the page filters (dates, branch, category, revenue basis). Left: every collection with units, share and revenue; right: the picked collection (revenue, units, share, orders, average price per unit, best branch, category split, top 8 products, branches). Area managers see it too, for their zone only (the rows are already filtered on the server). The Excel export does not include this section yet.

COLLECTIONS IN STAFF PERFORMANCE: the family of a sale is read from its item group ("Pandora Moments - Charm" -> Moments), so no extra data is needed. /staff has a "Sales by collection" card at the bottom (follows the store chip, the dates and the item groups counted; click a collection to see who sells it most). A sales person's own page has "Your collections" (their share per family against their store). Groups the super admin leaves out (packaging, services, jewellery boxes) stay out.

CHANGE STORE (Staff approvals): the super admin can move a sales person to another store with "Change store" (waiting, active and switched-off lists). The list holds the stores of the published sales file plus the sign-up stores. A linked account keeps its sales person name and its link moves to the new store (one account per sales person and store); a store manager automatically sees the new store. The person's numbers appear once the sales file lists them under that store (the page says so when it does not yet). Server action: setstore in api/accounts.js.

STOCK BALANCE (page /stock, API /api/stock -> api/erp.js?stock=1, helper api/_stock.js)
- Visible to the super admin, area managers (only their zone's warehouses) and the VM (pieces only, value zeroed on the server). Sales people and store managers never.
- Dates are changeable (From/To + presets) when ERP is connected: it runs ERPNext's "Stock Balance" report, cached 30 min (24 h for past dates). Super admin has "Refresh from ERP".
- The company comes from ERP_COMPANY or from the last "Sync from ERP" (erp/status.json). If neither exists, press Sync from ERP once.
- Excel path: All Uploads > Stock balance (the ERP Stock Balance report .xlsx). It is one fixed snapshot, so dates are locked. Used when ERP is off or fails.
- Categories are derived on the page from item group + item name (same rules as the dashboards); can also group by Collection. Click a row for locations and top items.
UPDATE: Stock balance now reads ONLY the Excel file added on All Uploads (Branches_Stock_Balance_All-Niche report). ERP is not used for stock; dates are those of that file.
UPDATE 2 (Oct 19): Stock balance is live from ERPNext again: it runs the Custom Report "Branches Stock Balance" (override the name with env ERP_STOCK_REPORT), no company needed, cached 30 min (24 h for past dates), super admin has "Refresh from ERP". If ERP fails, the last Excel file on All Uploads is shown with a note. New "Balance Qty by item" table on /stock: one column per branch plus the total.
STOCK SYNC STATUS: All Uploads > Stock balance shows "Last sync" (time, dates, stock lines, or the error) and a "Sync now" button (super admin). Stored in stock/status.json; updated by Sync now and by every ERP read. API: GET /api/stock?op=status, POST /api/stock?op=sync.
VM LIVE REPORT: the VM page (/vm) has a first card "Sales QTY and Volume by category - Jewelry" read live from the ERP Custom Report of that name (override with env VM_REPORT) for From/To dates the VM picks (quick buttons too). Server cleans it like an upload: only store/category/item/date/quantity columns are kept; money and "volume" columns are dropped. Cached 30 min (24 h for past ranges). The Category explorer follows the same dates. API: GET /api/vm?live=1&from=&to=, GET /api/vm?explorer=live&from=&to=. Excel uploads in All Uploads > VM Report still work as before.

ZONE STOCK (/vm/stock, api/_zonestock.js via /api/zonestock -> /api/vm?zonestock=1)
- Pieces of each SKU in each VM zone (zones come from VM Zones) plus "Back stock". Stored as events in zs/<store>.json.
- Count (typed, or the Stock Count tool's Excel export: sheet "Scan log", Zone + Matched SKU + Units; a Recount replaces) sets a zone.
  Receive adds to a zone, Move / Distribute takes from one zone to another (checked against stock now).
- ERP sales come off automatically: each piece from the display zone holding the most of that SKU, then back stock;
  the rest shows as "sold, not in any zone". Returns go to back stock. A day's counts/moves apply before that day's sales.
- Count differences = expected vs found at each count after the first. Pieces only, never money.
- Access: super admin + VM (all stores; VM cannot count or receive), store managers (role 'store') their own store only.

STOCK COUNT (/stockcount, private/stockcount.html, API /api/stockcount -> /api/vm?stockcount=1, helper api/_stockcount.js) - SUPER ADMIN ONLY
- Moved in from the standalone "pandora-stock-count" site. Load the ERP stock balance (.xlsx), scan barcodes (scanner or phone camera), see ERP vs Actual, recount the differences, export to Excel. Several devices share one count.
- Access: the page is served only to the super admin (api/site.js) and /api/stockcount checks the same login on every call (area managers, VM, store managers and sales people get 403). The old access code is gone; a signed-out browser is sent to /login.html.
- Shared count storage: the private store, not Redis. Documents are kept as sc/d/<path>.<time>.json (older versions removed after each write); sc/ver.json changes on every write and devices poll only that file every 4 s, reading more only when it changed. Counts from the old Redis site are not carried over.
- Product pictures (private/stockcount-pics-1..4.js, window.__PICS) are separate files because one Vercel response may not pass 4.5 MB; served to the super admin only.
- Blob operations: each save is a few writes/lists and every open device reads sc/ver.json every 4 s, so a long count with many devices uses a lot of Blob operations. If Vercel reports the Blob quota reached, move this helper to Upstash Redis (the old api/db.js of the stock count site did exactly that).
